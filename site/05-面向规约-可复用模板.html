面向规约开发 · 可复用模板

直接复制到新项目，按「____」填空即可。四套模板构成完整闭环。

模板 A · 需求规约转译表

用途：接到需求后，先转译成规约，再动手。填完这张表才算理解需求。

需求原文 涉及规约条款 规约要求 实现落点 验收标准
____ 宪法第 __ 条：____ ____ ____ ____
____ 设计文档：____ ____ ____ ____
____ 工程约定：____ ____ ____ ____

检查项：

  • ☐ 每条需求都能找到对应的规约条款
  • ☐ 没有「无规约可依」的需求（若有，先补规约）
  • ☐ 验收标准是可观察、可验证的（不是「做好」这类模糊表述）

模板 B · 实现自检清单

用途：功能实现完成后，逐条对照规约自检。只跑通功能不算完成。

数据与模型

  • ☐ 字段名称、类型是否与设计文档一致
  • ☐ 阈值 / 触发条件 / 默认值是否完全匹配
  • ☐ 命名约定（阶段名、变量名、函数名）是否统一

规约与边界

  • ☐ 是否满足宪法中的用户主权 / 隐私 / 安全条款
  • ☐ 是否遵循「外挂增强，最小化修改核心代码」原则
  • ☐ 是否引入了规约明令禁止的做法（如多余的视觉特效）

可回退与可维护

  • ☐ 新功能能否在不停用整体的情况下单独回退
  • ☐ 是否修改了不必要的既有代码
  • ☐ 关键决策是否在代码注释中回指了规约条款

验证与复现

  • ☐ 是否按验收标准逐条实测（而非目测）
  • ☐ 复查 / 回归流程是否已固化为脚本或命令
  • ☐ 结果是否符合预期，偏差是否已记录

模板 C · 项目记忆

用途：每个会话结束，把「既定决策」和「踩过的坑」沉淀下来，供跨会话复用。

## Hard Constraints（硬约束 · 不可违反）
- ____

## Engineering Conventions（工程约定 · 默认遵循）
- ____

## Lessons Learned（经验教训 · 避坑）
- ____

写入标准：

  • 硬约束写「底线」（如：用户数据默认本地化，不上传服务器）。
  • 约定写「默认做法」（如：新文件用 kebab-case，IIFE 模式）。
  • 教训写「原因 + 后果 + 正确做法」三要素。

模板 D · 偏差记录（反面教材）

用途：当实现偏离了规约，不要悄悄改掉，要记下来当教材。

偏差项 规约要求 实际实现 后果 / 影响 修正动作
____ ____ ____ ____ ____

示例（来自真实案例）：

偏差项 规约要求 实际实现 后果 修正动作
成长模型隐喻 设计为「水德」（水滴→溪流→江河→江海） 实现为「植物」（萌芽→小苗→树木→森林） 与设计文档不一致 按设计修正或更新设计

快速启动清单（新项目 6 步）

  1. [ ] 写 宪法（3～8 条价值观/边界，宁少勿滥）
  2. [ ] 为当前功能写一份 设计文档（数据模型 + 阈值 + 命名 + 状态机）
  3. [ ] 建 AGENTS.md 工程约定（技术约束 + 代码模式 + 复查清单）
  4. [ ] 跑通第一个闭环：需求 → 转译 → 实现 → 自检 → 记录偏差（模板 D）
  5. [ ] 会话结束写 项目记忆（模板 C）
  6. [ ] 设周期复审（定期审查是否偏离 + 规约是否仍正确）

一句话原则：先有规约，再写代码；实现回指规约，验证对照规约，经验反哺规约。
